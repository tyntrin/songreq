# แอพขอเพลงผ่าน QR — เอกสารออกแบบ (v1)

วันที่: 2026-11-16 · สถานะ: ผู้ใช้อนุมัติให้วางแผนและเริ่มสร้าง (2026-11-16)
ชื่อแอพ: ยังไม่ได้ตั้ง — ชื่อในโค้ดชั่วคราว `songreq` **[Claude]**
Mockup ที่อนุมัติแล้ว: https://claude.ai/artifact/B6HvfpHe6Ahgdqq4HgUjXy (หน้าลูกค้า 1–5, หน้านักดนตรี 6–12)

ป้าย **[Claude]** = การตัดสินใจของ Claude ที่ผู้ใช้ยังไม่ได้ยืนยัน แก้ได้

## 1. เจตนาและเหตุผล

- นักดนตรีใส่เพลงที่เล่นได้ ได้ QR ไปวางบนโต๊ะ ลูกค้าสแกนแล้วขอเพลงได้หลายเพลง ให้ทิปผ่านพร้อมเพย์หรือไม่ให้ก็ได้
- นักดนตรี **ตั้ง QR แล้วดูจออย่างเดียว** — ห้ามเพิ่มงานให้นักดนตรีระหว่างเล่น (ไม่มีปุ่มเปิด/ปิดรอบ ไม่มีปุ่มเล่นแล้ว/ข้าม)
- ทำเพื่อความพอใจของเจ้าของ และให้มี **เว็บที่มีคนใช้จริง** ไว้เป็นผลงานสมัครงาน; จะเปิดตัวพร้อมโปรเจกต์ Stage Sampler ของเจ้าของ (แต่หน้าตา **ไม่** ตาม Stage Sampler)
- **เวอร์ชันแรก = ฟีเจอร์ครบ ไม่เก็บเงินใคร** ไม่มีโฆษณา ไม่มีค่าธรรมเนียม

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / ต่อต้าน

**เป้าหมาย**
- นักดนตรีสมัครและพร้อมรับคำขอภายในไม่กี่นาที
- ลูกค้าสแกนแล้วขอเพลงได้ใน ~30 วินาที ไม่ต้องล็อกอินหรือลงแอพ
- คำขอขึ้นจอนักดนตรีแบบเรียลไทม์
- ต้นทุนรันจริง ≤ ~$4/เดือน

**ไม่ใช่เป้าหมาย (v1)**
- เนื้อร้อง/คอร์ด — เก็บแค่ชื่อเพลงและศิลปิน
- รับเงินผ่านระบบ, payment gateway, ตรวจสลิป, เด้งเข้าแอพธนาคารอัตโนมัติ (ทำไม่ได้กับพร้อมเพย์ส่วนตัว)
- แอพ native, โฆษณา, การเก็บเงินใด ๆ
- คิวลำดับเพลง, "กำลังเล่นตอนนี้", ปุ่มเล่นแล้ว/ข้าม

**ต่อต้าน**
- ลูกค้าต้องล็อกอิน/ลงแอพ/เห็นโฆษณาก่อนขอเพลง
- นักดนตรีต้องกดอะไรระหว่างเล่น
- หน้าลูกค้าช้าบนเน็ตมือถือ
- ค่าใช้จ่ายบานปลายโดยไม่รู้ตัว

## 3. โมเดลหลัก: "คืน" อัตโนมัติ

- QR รับคำขอ **ตลอดเวลา** (ค่าเริ่มต้น) นักดนตรีปิดได้ในหน้าตั้งค่า ("รับขอเพลง" สวิตช์ระดับเพจ) — ปิดแล้วลูกค้าเห็นรายการเพลงแต่ขอไม่ได้ (หน้า 5)
- **คืน (night)** = 06:00 ถึง 05:59 ของวันถัดไป เวลา `Asia/Bangkok` คำนวณจาก `created_at` ของคำขอ ไม่เก็บสถานะรอบในฐานข้อมูล
- **ร้าน** = setlist; แต่ละ setlist มี QR ของตัวเอง คำขอผูกกับ setlist ที่ถูกสแกน
- ชื่อร้าน/วันที่เป็นข้อมูลฝั่งนักดนตรี ลูกค้าไม่เห็น

## 4. ฟีเจอร์

### 4.1 ลูกค้า (ไม่ล็อกอิน ไม่มีโฆษณา) — mockup หน้า 1–5
- URL ของ QR: `/r/{setlistPublicId}`
- **หน้า 1 รายการเพลง**: หัวมีแค่รูป/อักษรย่อ + ชื่อวง + ป้าย "เปิดรับขอเพลง"; สลับภาษา TH·EN; ค้นหาชื่อเพลง/ศิลปิน; ชิปกรองตามแท็ก (จากแท็กของเพลงใน setlist) + "ทั้งหมด N"; แต่ละแถวมีปุ่มกลม +/✓ เลือกได้หลายเพลง; แถบล่าง "เลือกแล้ว N เพลง · ถัดไป"
- **หน้า 2 ส่งคำขอ**: รายการที่เลือก (เอาออกได้), ชื่อหรือโต๊ะ (ไม่บังคับ, ≤40 ตัวอักษร), ข้อความถึงนักดนตรี (ไม่บังคับ, ≤140), ทิป: ไม่ให้ / 20 / 50 / 100 / 200 / ใส่เอง (1–10,000 บาท); ปุ่มเปลี่ยนข้อความตามทิป; ไม่ให้ทิป → ส่งแล้วไปหน้า 4; มีทิป → ส่งแล้วไปหน้า 3
- **หน้า 3 พร้อมเพย์**: ยอด, QR พร้อมเพย์ใส่ยอด (EMVCo payload จากพร้อมเพย์ของนักดนตรี), ชื่อวง, เลขพร้อมเพย์ปิดเหลือ 4 ตัวท้าย, วิธีโอน 3 ขั้น, ปุ่ม "บันทึกรูป QR" (ดาวน์โหลด PNG), ปุ่ม "โอนแล้ว" (บันทึก `tip_claimed_at`), ลิงก์ "ข้าม ส่งคำขอโดยไม่โอน" (ยอดทิปไม่ถูกนับ)
  - คำขอถูกบันทึก **ก่อน** หน้า 3 (ตอนกดส่งในหน้า 2) พร้อม `tip_amount` ที่ตั้งใจ; ทิปถูกนับในสถิติเฉพาะเมื่อกด "โอนแล้ว"
- **หน้า 4 สถานะ**: "ส่งคำขอถึง {ชื่อวง} แล้ว"; แต่ละเพลงสถานะ **ส่งแล้ว** หรือ **นักดนตรีเห็นแล้ว**; กล่อง "แจ้งโอนทิป ฿X แล้ว" ถ้ากดโอนแล้ว; แสดงเฉพาะคำขอของ **เครื่องนี้ในคืนนี้**; อัปเดตเรียลไทม์; ปุ่ม "ขอเพลงเพิ่ม"
- **หน้า 5 ปิดรับชั่วคราว**: เห็นรายการเพลงแต่ไม่มีปุ่มเลือก + กล่องอธิบาย
- ภาษา: ไทย/อังกฤษ เลือกจาก `Accept-Language` และสลับเองได้ (เก็บใน cookie) **[Claude]**
- ตัวระบุเครื่อง: cookie `sr_device` สุ่ม (httpOnly, 1 ปี)

### 4.2 นักดนตรี (ล็อกอิน) — mockup หน้า 6–12
- **หน้า 6 เข้าสู่ระบบ**: LINE, Google (Auth.js) — ใน dev/test มี provider "Dev login" เปิดเฉพาะเมื่อ `AUTH_DEV_LOGIN=true` และไม่ใช่ production **[Claude]**
- **หน้า 7 ตั้งค่าเพจครั้งแรก**: รูป (ไม่บังคับ), ชื่อวง/ศิลปิน, พร้อมเพย์ เบอร์มือถือ (10 หลัก ขึ้นต้น 0) หรือเลขบัตรประชาชน (13 หลัก ตรวจ checksum) → ไปหน้าคลังเพลง; ระบบสร้าง setlist แรกชื่อ "Setlist หลัก" ให้อัตโนมัติ **[Claude]**
- เมนูล่าง 5 แท็บ: คำขอ / เพลง / QR / สถิติ / ตั้งค่า
- **หน้า 8 จอดูคำขอ (คืนนี้)**:
  - การ์ดสรุป: จำนวนคำขอคืนนี้, ทิปที่ลูกค้าแจ้ง (นับเฉพาะที่กดโอนแล้ว)
  - ชิปกรอง: ทุก QR / แต่ละ setlist
  - การ์ดคำขอ **รวมตามเพลง** ภายในคืน: ชื่อเพลงตัวใหญ่, ศิลปิน, ป้าย "ใหม่" (ยังไม่เคยแสดงบนจอนี้), "ขอ N ครั้ง", ข้อความล่าสุดของลูกค้า (ถ้ามี), ผู้ขอ ("โต๊ะ 7 · มิ้น" / "โต๊ะ 3 และอีก 2 คน" / "ไม่ระบุชื่อ"), เวลาล่าสุด, ทิปรวมที่แจ้ง; เรียงตามคำขอล่าสุดก่อน
  - ปุ่มเปิด/ปิดเสียงแจ้งเตือน (เก็บใน localStorage); เสียง + สั่นเมื่อมีคำขอใหม่; Wake Lock กันจอดับ
  - **ไม่มีปุ่มจัดการคำขอ**; เมื่อคำขอถูกส่งถึงจอนี้ ระบบบันทึก `seen_at` อัตโนมัติ (ลูกค้าเห็น "นักดนตรีเห็นแล้ว")
  - ปุ่มซ่อนคำขอที่ไม่เหมาะสม / บล็อกเครื่อง อยู่ในเมนู ⋯ ของการ์ด (ไม่ต้องใช้ระหว่างเล่นปกติ) **[Claude]**
- **หน้า 9 คลังเพลง**: ค้นหา iTunes Search API (`country=TH`, `entity=song`, `limit=15`) ผ่าน API ของเราเอง (มีแคช); ผลลัพธ์มีปุ่ม "+ เพิ่ม"/"มีแล้ว"; "ไม่เจอเพลงที่หา? เพิ่มเอง"; รายการ "เพลงของฉัน" พร้อมคีย์และแท็ก; เมนู ⋯ แก้คีย์/แท็ก/ลบ; เพลงที่เพิ่มใหม่ถูกใส่ใน setlist หลักอัตโนมัติ **[Claude]**
- **หน้า 10 Setlist และ QR**: การ์ดต่อ setlist (ชื่อ, จำนวนเพลง, คำขอคืนนี้), ตัวอย่างโปสเตอร์, ดาวน์โหลดโปสเตอร์ A5 (PDF หรือ PNG สร้างฝั่ง client) และ PNG ของ QR, คัดลอกลิงก์, แก้รายการเพลงใน setlist (ติ๊กเลือกจากคลัง), สร้าง setlist ใหม่
- **หน้า 11 สถิติ**: ช่วง คืนนี้ / 7 วัน / เดือนนี้ (เดือนปฏิทินตามเวลาไทย); คำขอ, ทิปที่แจ้ง, จำนวนคืนที่มีคำขอ; 5 เพลงที่ถูกขอบ่อย (แถบ); แยกตาม setlist; หมายเหตุว่าทิปไม่ได้ตรวจกับธนาคาร
- **หน้า 12 ตั้งค่า**: แก้โปรไฟล์ (ชื่อ, รูป, พร้อมเพย์), สวิตช์ "รับขอเพลง", สวิตช์เสียงแจ้งเตือน, สมาชิกวง (owner/member) + ส่งลิงก์เชิญ (หมดอายุ 7 วัน), ออกจากระบบ
- สิทธิ์: owner ทำได้ทุกอย่าง; member ทำได้ทุกอย่างยกเว้นแก้พร้อมเพย์ เชิญ/ลบสมาชิก **[Claude]**
- ผู้ใช้หนึ่งคนอยู่ได้หลายเพจ — v1 UI แสดงเพจแรกเป็นหลัก มีตัวสลับเพจถ้ามีมากกว่า 1 **[Claude]**

## 6. สถาปัตยกรรม

**ผู้ใช้ตัดสินใจแล้ว**: Next.js 16 (App Router) + React 19 + TypeScript; PostgreSQL + Drizzle ORM; Auth.js (LINE + Google); GitHub + GitHub Actions; GCP `e2-micro` รัน pm2 + Postgres เครื่องเดียว; Cloudflare หน้าเว็บ + R2

**[Claude]**
- Region `us-west1`, Standard network tier (ส่งออกฟรี 200 GiB/เดือน), standard persistent disk 30 GB, swap 2 GB
- **ห้าม build บน VM**: GitHub Actions build (`output: "standalone"`) → อัปโหลด artifact → `deploy.sh` (สลับ build, `pm2 reload`, health check, auto-rollback) แบบ GemHub
- Caddy reverse proxy + Cloudflare Origin Certificate (Full strict); firewall 443 เฉพาะ IP Cloudflare
- **เรียลไทม์**: SSE (`text/event-stream`) จาก route handler + **event bus ในโปรเซส** (EventEmitter) — pm2 รัน 1 โปรเซส จึงไม่ต้องใช้ `LISTEN/NOTIFY`; ซ่อนไว้หลัง interface `RealtimeBus` เพื่อเปลี่ยนเป็น `LISTEN/NOTIFY` ได้ภายหลัง; heartbeat ทุก 25 วินาที; client reconnect เอง + fallback polling 15 วินาที
- **ฐานข้อมูล**: production ใช้ `postgres` (postgres.js); local dev และเทสต์ใช้ **PGlite** (Postgres ใน Node) เพราะเครื่อง dev ไม่มี Postgres/Docker — schema เดียวกัน (drizzle `pg-core`)
- รูป: อัปโหลดไป R2 ผ่าน presigned URL ใน production; local dev เก็บใน `./.data/uploads` (driver สลับด้วย env)
- Backup: cron `pg_dump` → R2 ทุกคืน เก็บ 14 วัน; runbook restore
- GCP budget alert $5, uptime monitor ยิง `/api/health`
- โดเมน: กำหนดผ่าน env `APP_URL`

## 7. ข้อมูล **[Claude]**

- Auth.js: `users` (+ `isAdmin` คำนวณจาก env ไม่เก็บ), `accounts`, `sessions`, `verification_tokens`
- `performers` — id, slug unique, display_name, avatar_url, promptpay_type (`phone`|`national_id`), promptpay_id, accepting_requests (default true), suspended_at, created_at
- `performer_members` — performer_id, user_id, role (`owner`|`member`), unique(performer_id,user_id)
- `performer_invites` — token unique, performer_id, created_by, expires_at, used_at
- `songs` — id, title, artist, source (`itunes`|`custom`), itunes_track_id unique nullable, created_by
- `repertoire` — id, performer_id, song_id, song_key, tags text[], notes, created_at; unique(performer_id,song_id)
- `setlists` — id, performer_id, name, public_id unique (สุ่ม 10 ตัว), created_at
- `setlist_songs` — setlist_id, song_id, position; pk(setlist_id,song_id)
- `requests` — id, setlist_id, performer_id, device_id, requester_name, message, tip_amount (int บาท, 0 = ไม่ให้), tip_claimed_at, hidden_at, created_at
- `request_items` — id, request_id, song_id, seen_at
- `blocked_devices` — performer_id, device_id, created_at; pk(performer_id,device_id)
- PDPA: ลบ requester_name/message ที่เก่ากว่า 90 วัน (งาน cron) และหน้านโยบายความเป็นส่วนตัวสั้น ๆ
